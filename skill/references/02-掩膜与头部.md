# 02 · 掩膜与头部

> 这是两个 skill 唯一重合的地方，也是整条流水线的**唯一掩膜来源**。
> 裁切要 core/full/头心，曝光要 L_in/L_box——全部来自同一次 `analyze()`。

## 1. 唯一链路

```python
from nef_io import preview_pil, sensor_size, read_exif
from mask_head import analyze, count_subjects

prev = preview_pil(nef)            # 8256×5504 内嵌全幅 JPEG（约 430 ms）
res  = analyze(prev, size=768)     # 一次前向
res["mask"]    # 768×768 uint8，对应整幅归一化
res["core"]    # (l,t,r,b) 躯干框
res["full"]    # (l,t,r,b) 含附肢
res["head"]    # (x,y) 或 None
res["mask_size"]  # 实际用的分辨率（降级时会是 384）
```

**坐标天然是全画幅归一化**：整幅缩到 768×768 时，掩膜上的 (u,v) 就是
(占宽比例, 占高比例)，中间不做任何映射。这是它比 JPG 链路少一层误差的原因。

## 2. 为什么必须全画幅

推理端只有 RAW。任何依赖成品 JPG 的方案，在真实用途上都不可用——
裁切正是要产出的东西，不可能先有成品。

实测（100 张，同一套公式、同一个真值，只换掩膜来源）：

| 链路 | IoU 中位 | 均值 | <0.5 | 耗时 |
|---|---:|---:|---:|---:|
| 成品 JPG@512 → 映射回全幅 | 0.8710 | 0.8510 | **0 张** | — |
| 全幅@512 | 0.8670 | 0.8225 | 5 张 | 1.06 s |
| 两阶段（384 粗 + 局部 512） | 0.8673 | 0.7869 | **10 张** | 1.41 s |
| **全幅@768** | **0.8739** | **0.8250** | 5 张 | 1.60 s |

1. 全画幅不比 JPG 链路差，中位甚至高 0.003；
2. **中位不降反升，但长尾变差**：JPG 链路一张都没掉到 0.5 以下，全幅两条各掉 5 张——
   全是虫宽 <8% 的小虫，不是分辨率不够，是虫在全幅里占的像素太少；
3. **不要用两阶段**：局部块里虫子占满画面，开运算边界效应变强，失败 10 张；
4. 512 比 768 低 **0.7 个点**，显存紧张时可以退。

> 这组数字衡量的是"掩膜链路"，不含公式误差，所以比端到端留出（0.8650）高。

## 3. 本体 / 附肢怎么拆：开运算，不是重建

`split_body_core(mask, r_scale=0.035)`

语义是「**局部厚度 ≥ 2r 的部分算身体**」，而这正是形态学开运算的定义。

**不能用测地重建**：重建会把与身体连通的腿全部并进 core，而腿正是要排除的。

```
r    = max(1, round(0.035 · √area))
core = open(mask, 圆盘(r))
full = 掩膜外接框
```

补充两条：
- core 为空时退到 r/2，再退到 1；
- 只保留最大连通域，但把离主块 ≤2r+1 的碎块并回（腿根断裂）。

**参数为什么是 0.035**：按 √area 自适应，能容纳从跳虫到蜻蜓两个数量级的尺寸差。
固定像素半径必然在某一端失效。

## 4. 多主体判定

`count_subjects(mask, ratio=0.08)`：最大连通域之外，还有几个面积超过主块 8% 的主体。

- 同一只虫被触角/腿断开 → 碎块通常远小于 8%，不会误判；
- 真出现第二只虫（交配对、两只并排）→ 第二块一般 >8%；
- 判错的代价可控：多判 → 关掉头部项（略保守）；漏判 → 头项作用在两只的中点（框心会偏）。

**多主体时强制 `head=None`**，裁切公式的头 4 项置 0，仍出框（规则 12）。

## 5. 头部关键点

```
core 框外扩 15% → 裁 256×256
  → ResNet50(IMAGENET1K_V2) stem+layer1+layer2
  → layer3(/16, 1024ch) + layer4(/32, 2048ch) 双尺度融合 → 256ch
  → 3×3 卷积头 → 64×64 热力图
  → softmax + soft-argmax → (u,v)
  → 映射回全画幅归一化
```

权重 `assets/weights/head_kp_v2.pth`（94 MB），推理 30 ms/张（1650 fp32）。

**不要从零训 CNN。** 同一数据集、同一损失：

| 方案 | 命中率 |
|---|---:|
| 从零训 4 层卷积 + MSE | 5% |
| 从零训 + 软目标交叉熵 | 22% |
| **ResNet50(ImageNet) + 软目标交叉熵** | **90%** |

从零训时五折 loss 全部收敛到同一个值（3.79–3.81），说明它学的是**位置先验**，不是图像。
判据：看 `pred_std`——塌陷时 ≈0，正常 0.24–0.27。

**判据（2026-11-17 修正）**：原写「置信度 <0.05 时 head=None」，但实测这个网络的
softmax 峰值本来就很平——15 张 / 5 批次 conf 只有 **0.034–0.064**（中位 0.056），
阈值 0.05 正好卡在分布正中间，等于把约 1/3 预测正确的头点丢掉（软件里表现为
「很多照片没有头部」）。放大核对过被判丢弃的三张（瓢虫幼虫 / 交配对上方那只 /
花金龟），点都确实落在头上。

现在改为两条同时满足：

- `conf ≥ HEAD_CONF_MIN = 0.02`（只滤掉完全发散的图）
- `head_inside(core, head, slack=0.20)`：头点必须落在身体框外扩 20% 之内（几何兜底）

同一批 15 张从保留 10 张变成 15 张。**代价**：真没头的场景（纯背面、蜷缩）也会给一个
「大致靠前」的点，裁切会带一点头部偏移——软件里可以手动拖。

## 6. 显存与降级

| 输入 | 耗时（空闲） | 显存峰值 |
|---|---:|---:|
| 512 | 0.71 s | 1.51 GB |
| 768 | 1.22 s | 2.28 GB |
| 1024 | — | **OOM（4 GB 卡）** |

Windows 桌面（dwm/explorer/SearchHost/浏览器）常态吃 1.5–3.6 GB。
桌面占用 >2 GB 时 768 会从 1.22 s 变成 3.01 s（WDDM 分页），或者直接失败。

`analyze()` 的兜底：遇到显存类错误（`OutOfMemory`、`CUBLAS_STATUS_NOT_INITIALIZED`、
`LibRawMemPoolOverflow`）会清缓存后降到一半（768→384）重试一次，
返回值里标 `degraded=True`，`params.csv` 的 note 会带上。

## 7. 已知弱点

**① 小虫**：虫宽占全幅 <8% 时，768 输入下虫子只有 20–60 px，掩膜会糊。
100 张里有 5 张裁切 IoU <0.5。处理方式不是整体拉到 1024，而是跑批时输出
「虫宽占全幅 %」，把 <10% 的挑出来人工过一眼。

**② 拟态与宿主同色**：绿蛾停在绿叶上、竹节虫停在竹枝上时，BiRefNet 可能把宿主的
一部分当成虫体。实测影响比看上去小（`split_body_core` 的开运算会把叶片边缘切掉），
但要跑批时扫一眼叠加图；**不要据此设阈值自动剔除**——目前没有数据支持任何阈值。

**③ 非昆虫照**：目录里混进的风景/花絮照会 `mask_empty`。这是正常的，不是 bug。

## 8. 失败与补救

| 现象 | 原因 | 处理 |
|---|---|---|
| 掩膜为空（`mask.sum()<50`） | 极暗、极低对比、主体太小、非昆虫 | 先提亮（gamma 0.5）重跑一次；仍失败则记录跳过 |
| 掩膜把背景吃进来 | 背景纹理像虫 | 只保留最大连通域；`--seg-size 512` 常能改善 |
| 框比虫大一圈 | 同上 | 看叠加图，必要时人工 |

**不要用 SAM3 兜底。** 实测两者错误模式不同、不是强弱关系：
最差 10 张里 SAM3 更好 5 张、更差 5 张，还有把整幅当虫的溢出。

## 9. 一条工程纪律

**掩膜只算一次，两处复用。**

如果裁切和曝光各跑一遍 BiRefNet，或者在两种分辨率下各算一次，
会得到两套互不相容的框——这种错不会报错，只会静默给出错的答案。

变量名也要注意：全幅预览是 8256×5504，如果主循环里写 `W, H = prev.size`
覆盖了外层的目标尺寸 `H`，会把中间图 resize 成全幅。**凡在分支里解包尺寸，一律带前缀。**
